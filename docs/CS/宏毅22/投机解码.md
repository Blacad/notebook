# 投机解码原理
---
投机解码，也叫 **Speculative Decoding**，核心目标是：

**在不明显改变大模型输出分布的前提下，加速自回归生成。**

它解决的问题是：大模型生成文本时通常要 **一个 token 一个 token 串行生成**，每生成一个 token 都要跑一次大模型，非常慢。

---

## 1. 普通自回归解码为什么慢？

假设大模型是目标模型 (M_q)，生成序列：

[  
y_1, y_2, y_3, \dots  
]

普通解码流程是：

```text
输入 prompt
大模型生成 y1
把 prompt + y1 输入大模型
大模型生成 y2
把 prompt + y1 + y2 输入大模型
大模型生成 y3
...
```

也就是说，大模型每次只能确定下一个 token：

[  
p(y_t | x, y_{<t})  
]

所以生成 (T) 个 token，至少要调用目标大模型 (T) 次。

---

## 2. 投机解码的核心思想

投机解码引入一个 **小模型 / 草稿模型** (M_p)。

它比目标大模型小很多，速度快，但质量差一点。

流程是：

```text
草稿模型先快速连续生成 K 个候选 token
目标大模型一次性并行验证这 K 个 token
接受其中正确的部分
如果有 token 被拒绝，就从目标模型分布中重新采样
```

简单说：

> 小模型负责“猜”；大模型负责“批改”。

---

## 3. 关键流程

假设当前上下文是：

```text
The capital of France is
```

草稿模型快速生成 (K=4) 个 token：

```text
Paris . It is
```

也就是候选序列：

[  
\tilde{y}_1, \tilde{y}_2, \tilde{y}_3, \tilde{y}_4  
]

然后目标模型不是一个个生成，而是一次 forward 验证整个序列：

```text
The capital of France is Paris . It is
```

目标模型可以并行计算每个位置的概率：

[  
q(\tilde{y}_1), q(\tilde{y}_2), q(\tilde{y}_3), q(\tilde{y}_4)  
]

同时草稿模型也有自己的概率：

[  
p(\tilde{y}_1), p(\tilde{y}_2), p(\tilde{y}_3), p(\tilde{y}_4)  
]

然后逐个判断这些 token 是否接受。

---

## 4. 为什么目标模型可以并行验证？

这是理解投机解码最关键的一点。

Transformer 在训练或验证一个完整序列时，本来就可以一次性计算所有位置的 next-token 分布。

例如输入：

```text
x1 x2 x3 x4
```

经过 causal mask 后，模型会同时输出：

```text
位置1预测 x2
位置2预测 x3
位置3预测 x4
位置4预测 x5
```

虽然注意力是 causal 的，但矩阵计算可以并行完成。

所以在投机解码中，目标模型一次 forward 可以得到：

[  
q(y_1 | x), \quad q(y_2 | x,y_1), \quad q(y_3 | x,y_1,y_2), \dots  
]

这就是它能“并行验证”多个草稿 token 的原因。

注意：**并行验证不等于目标模型并行生成多个未知 token**。  
目标模型只是验证草稿模型已经给出的候选 token，因此整个候选序列已经确定，可以一次性喂进去。

---

## 5. 接受-拒绝机制

假设草稿模型分布是 (p)，目标模型分布是 (q)。

对于草稿模型生成的 token (\tilde{y}_t)，接受概率通常是：

[  
\alpha_t = \min \left(1, \frac{q(\tilde{y}_t)}{p(\tilde{y}_t)} \right)  
]

含义是：

如果目标模型认为这个 token 的概率比草稿模型还高：

[  
q(\tilde{y}_t) \ge p(\tilde{y}_t)  
]

那就直接接受。

如果目标模型认为它概率较低：

[  
q(\tilde{y}_t) < p(\tilde{y}_t)  
]

那就以比例

[  
\frac{q(\tilde{y}_t)}{p(\tilde{y}_t)}  
]

接受。

如果某个 token 被拒绝，那么后面的草稿 token 都不能继续用了，因为上下文已经变了。

---

## 6. 被拒绝后怎么办？

假设草稿模型生成：

```text
A B C D
```

目标模型验证时：

```text
A 接受
B 接受
C 拒绝
```

那么最终保留：

```text
A B
```

然后在位置 C 处，不能直接用草稿模型的 C，也不能直接从目标模型原始分布 (q) 采样，而是从一个修正分布中采样：

[  
q'(x) = \frac{\max(q(x)-p(x),0)}{\sum_x \max(q(x)-p(x),0)}  
]

直觉是：

> 草稿模型已经“过度提出”的部分要扣掉，剩下的概率质量再由目标模型补充。

这样可以保证整体采样分布仍然等价于直接从目标模型采样。

---

## 7. 一个直观例子

目标模型是一个认真但很慢的老师。  
草稿模型是一个快但不太准的学生。

普通解码：

```text
老师写第1个字
老师写第2个字
老师写第3个字
老师写第4个字
```

投机解码：

```text
学生先写4个字
老师一次性检查这4个字
前3个都对，直接采用
第4个不对，老师改写第4个
```

如果学生经常猜对，老师每次检查一次就能确认多个 token，于是速度变快。

---

## 8. 投机解码为什么能加速？

因为草稿模型很小，生成 (K) 个 token 的成本较低。

目标模型虽然还是要 forward，但它一次 forward 可以验证多个 token。

普通解码：

[  
K \text{ 个 token} \Rightarrow K \text{ 次目标模型 forward}  
]

投机解码：

[  
K \text{ 个草稿 token} \Rightarrow 1 \text{ 次目标模型 forward} + K \text{ 次小模型 forward}  
]

如果小模型足够快，而且接受率高，就能明显加速。

---

## 9. 什么时候加速效果好？

投机解码效果主要取决于两个因素：

### 第一，草稿模型要快

如果草稿模型不够小，那么草稿阶段本身就很耗时，加速收益会下降。

### 第二，草稿模型要准

如果草稿模型生成的 token 经常被目标模型接受，那么一次验证可以接受多个 token。

如果接受率很低，经常只接受 0 个或 1 个 token，那么效果就差。

因此理想情况是：

```text
草稿模型小很多，但分布尽量接近目标模型
```

---

## 10. 和普通并行生成的区别

容易误解的一点是：

**投机解码不是让大模型真正同时生成多个未来 token。**

因为自回归模型中：

[  
y_3  
]

依赖于：

[  
y_1, y_2  
]

所以目标模型自己不能直接跳过前面 token 生成后面的 token。

投机解码做的是：

```text
草稿模型先把未来 token 猜出来
目标模型基于这些已知候选，一次性验证
```

所以它是：

```text
猜测未来 + 并行验证
```

而不是：

```text
目标模型直接并行生成未来
```

---

## 11. 总结

投机解码可以概括为一句话：

> 用一个快速小模型提前生成多个候选 token，再让慢速大模型一次性并行验证这些候选，从而把多次大模型串行解码压缩成较少的大模型 forward。

它的关键点是：

```text
草稿模型：串行但便宜地生成 K 个 token
目标模型：一次 forward 并行验证 K 个 token
接受机制：保证最终分布仍然等价于目标模型采样
加速来源：减少目标大模型的调用次数
```

所以你之前问的“草稿模型生成 K 个候选 token 不也需要串行生成吗”——是的，**草稿模型仍然串行生成**，但因为它小很多、快很多，所以整体仍然可能加速。


# DSpark
---
**你理解得对：传统的自回归草稿模型生成 (K) 个 token，确实也需要串行执行 (K) 次。**

区别在于：草稿模型通常远小于目标模型，所以虽然也是串行，但每一步便宜很多。

假设：

- 目标模型一次前向耗时 (T_{\text{target}})
    
- 草稿模型一次前向耗时 (T_{\text{draft}})
    
- 且 (T_{\text{draft}}\ll T_{\text{target}})
    

普通解码生成 (K) 个 token 的成本约为：

[  
K T_{\text{target}}  
]

传统推测解码的成本约为：

[  
K T_{\text{draft}}+T_{\text{target-verify}}  
]

目标模型可以通过一次带有 (K) 个位置的前向传播，并行算出整段草稿 token 对应的 logits，因此不需要再串行运行 (K) 次目标模型。

例如：

[  
T_{\text{target}}=100\text{ ms},\qquad  
T_{\text{draft}}=5\text{ ms}  
]

生成并成功接受 4 个 token：

- 普通解码：(4\times100=400) ms
    
- 推测解码：(4\times5+100=120) ms
    

即使草稿阶段串行，仍然可能更快。

## DSpark 为什么又不完全一样

DSpark 正是试图进一步解决：

> 草稿模型串行生成 (K) 次，本身也会成为瓶颈。

它采用的是**半自回归草稿生成**，不是让一个完整小语言模型严格串行运行 (K) 次。

可以粗略理解为两部分：

[  
\text{并行块预测}  
+  
\text{轻量顺序修正}  
]

大部分昂贵的表示计算由并行 backbone 一次完成，然后使用很轻量的顺序模块，让后一个草稿位置能够获得前一个位置的信息。这样既不像完全并行方法那样忽略 token 间依赖，也不像传统自回归草稿模型那样，对每个 token 都完整运行一次 Transformer。DSpark 的目标就是在并行速度和自回归依赖之间折中。([alphaXiv](https://www.alphaxiv.org/overview/2026.dspark?utm_source=chatgpt.com "DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation | alphaXiv"))

可以对比为：

### 传统自回归草稿模型

[  
h_1=\operatorname{DraftTransformer}(x)  
]

[  
h_2=\operatorname{DraftTransformer}(x,y_1)  
]

[  
h_3=\operatorname{DraftTransformer}(x,y_1,y_2)  
]

完整草稿网络执行 (K) 次。

### 完全并行草稿模型

[  
(h_1,h_2,\ldots,h_K)

\operatorname{ParallelDraft}(x)  
]

只执行一次，但 (h_3) 无法充分利用实际预测的 (y_1,y_2)，所以越靠后的 token 往往越不准确。

### DSpark 半自回归

可以抽象为：

[  
(h_1^{(0)},\ldots,h_K^{(0)})

\operatorname{ParallelBackbone}(x)  
]

然后做轻量顺序更新：

[  
h_i

g\left(h_i^{(0)},h_{i-1},y_{i-1}\right)  
]

这里的 (g) 比完整 Transformer 小得多。因此，严格来说，它仍然包含一定的顺序依赖，但不是完整大模型或完整草稿模型串行运行 (K) 次。

所以更准确的结论是：

> **传统 speculative decoding 的草稿阶段通常确实是串行的，只是模型小；DSpark 则进一步把草稿生成中的主要计算并行化，只保留低成本的轻量串行部分。**

另外，推测解码的收益还取决于接受长度。如果草稿生成了 (K=8) 个 token，但目标模型只接受前两个，那么后六个草稿位置的计算就浪费了。DSpark 还会根据置信度动态控制验证长度，以减少这种无效计算。([alphaXiv](https://www.alphaxiv.org/audio/2026.dspark?utm_source=chatgpt.com "DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation | alphaXiv"))
